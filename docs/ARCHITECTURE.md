# Architecture

Companion to [spec.md](spec.md) §4–§6; this documents how the tree
realises them, the decisions the spec left open, and where the Rust
design departs from the spec's original C++ text (the spec carries the
amendments in §3.3, §4, §12, §13 and §15).

## Layers

`tuuli_core::engine::Engine` is the seam the spec asks for in §4.1:
nothing above `engine.rs` names a Servo type, so an out-of-process content
model in M4 can replace `ServoEngine` with an IPC proxy without touching
the Qt layer, the models or the QML.

### Why Rust, and why no C ABI

The engine's embedding API is Rust.  Consuming it through `servo_capi`
(the spec's original plan) would have put a C ABI, a C++ shim and a
cbindgen header between two Rust code bases, and every monthly rebase
would have had to reconcile all three.  So the browser is Rust throughout
and links libservo directly.  Qt is reached with qmetaobject-rs: each
`#[derive(QObject)]` struct becomes a Qt meta-object whose properties,
signals and invokables QML uses like any C++ type.  C++ exists only where
Qt has no Rust binding — the `QQuickFramebufferObject` subclass and its
`Renderer`, `SailfishApp`, `QQuickImageProvider`, `QDBusInterface` — and
is written inline in `cpp!` blocks next to the Rust that calls it.  The
Servo-linked packages (`servo/backend`, `servo/app`) are outside the cargo
workspace so that host builds and CI never clone Servo.

## Threads

| Thread | Owns | Code |
|---|---|---|
| Qt GUI | QML, input, the core, every engine call, Servo's event loop, **painting** | `WebViewItem`, `core.rs`, `Browser`, `ServoEngine` |
| Servo internal | script, layout, style, net, image decode | libservo |

This departs from spec §4.2, which put painting on Qt's render thread.
A libservo embedder cannot do that: `Servo`, `WebView` and the delegates
are single-thread types, and `paint` is a method on the same `WebView` the
GUI thread drives.  Tuuli therefore runs the scene graph with
`QSG_RENDER_LOOP=basic`, which `tuuli_browser::run` sets before the
`QGuiApplication` exists.  Rendering happens on the GUI thread inside
`TuuliFboRenderer::render()` with the scene-graph context current, and
the render lock the spec's design needed does not exist because the
thread it guarded against does not.  The cost is that QML no longer
renders concurrently with its own animations; with one FBO item on one
panel this is inside the §11 budget.  The gain is that spec §5.3's
thread-affinity risk on the hybris driver disappears: every GL call of
the process is made on one thread.

Rules, in code:

- The core (`tuuli_core::Browser`) lives in a thread-local on the GUI
  thread (`core.rs`).  `with_core` is the only way to reach it and it
  panics off-thread; `with_core_opt` returns `None` there, which is how
  `render()` detects a threaded render loop and logs the fix.
- Engine events are delivered only from inside `Engine::spin_event_loop`,
  never re-entrantly from an engine call, and they are queued as data
  (`WebViewEvent` → `TabEvent`, `BrowserEvent`, `DownloadEvent`) rather
  than dispatched.  The Qt layer drains the queues with `pump()` after
  every core call and every spin, and only then touches Qt objects.  This
  is what allows the Qt objects to hold no borrows across engine calls:
  qmetaobject-rs keeps each object in a `RefCell`, and a re-entrant
  mutable borrow is a panic, not a deadlock.
- Servo's waker is the only cross-thread entry.  `Engine::set_waker`
  installs a closure that posts a `queued_callback` to the GUI thread; the
  callback spins the engine and pumps.  No other Servo callback reaches Qt.
- No Qt object is created on a Servo thread and nothing in `tuuli-core`
  knows Qt.

### Engine initialisation on first render

Initialising Servo compiles WebRender's shader set and needs a current GL
context (spec 5.3).  The first `TuuliFboRenderer::render()` creates the
`QtRenderingContext` around the scene-graph context and the item's FBO
and calls `Browser::initialize_engine`.  `EngineEvent::Initialized`
arrives on the next spin; `TabList::on_engine_initialized` then
materialises the current tab's webview.  Until that moment tabs exist
without engine webviews (they also do after a context loss, and when the
live-webview budget evicts them).  If initialisation fails, the failure is
final: `engineFailed` is raised on the item and the chrome shows the
error page.

### Scene-graph invalidation

`WebViewItem` sets the window's persistent-context and persistent-scene-
graph flags, so covering or sleeping the app normally keeps the context.
If Qt nevertheless destroys the renderer (`~TuuliFboRenderer`), the
destructor calls `render_context_lost()`, which shuts the engine down
rather than leaking GL objects (spec 5.2).  `Browser::on_render_context_lost`
detaches every webview but keeps URLs, titles, scroll and zoom, and
publishes `BrowserEvent::RenderContextLost`; the next render
re-initialises and the current tab is re-created lazily, restoring its
viewport after load.  Session restore and context loss share this path
deliberately.  The renderer holds only a `QPointer` to the item and never
borrows it: the scene graph deletes the node after the item at window
shutdown.

## Rendering

The QML `WebView` is `Rust_WebViewItem : RustObject<QQuickFramebufferObject>`
in `webview.rs` (spec 5.1).  The FBO is created with a combined
depth/stencil attachment (WebRender needs depth).  `QtRenderingContext`
implements `tuuli_core::engine::RenderingContext`; the backend wraps it in
libservo's `RenderingContext`: `make_current` is a check that the
scene-graph context is current on the calling thread, `present` is a
no-op, `framebuffer_object` returns the FBO Qt bound for this frame,
`proc_address` goes to `QOpenGLContext::getProcAddress`.  The reported GL
version is GLES 3.2 whenever the driver reports GLES ≥ 3.0 (spec 5.2).
After Servo paints, the renderer calls `QQuickWindow::resetOpenGLState()`.

When the engine paints nothing (mock engine, engine not ready, init
failure) the renderer clears the FBO with the item's `placeholderColor`.
Frame times are accumulated into `PerfLog` when performance logging is on.

## Input

`TouchConverter` (`input.rs`) turns the item's touch points into
`TouchPoint`s carrying both device px (for edge zones) and CSS px (for the
engine), dropping stationary points and cancelling everything on
`TouchCancel`.  DPR is not hard-coded: `derive_device_pixel_ratio`
(`geometry.rs`) uses Qt's ratio when it is above 1 and otherwise derives
it from the panel's physical DPI (Android's dpi/160 rule, rounded to
0.25), with a developer override.

`GestureArbiter` (`gesture.rs`, spec 6.2) owns one touch sequence at a
time and is driven with explicit timestamps so it is testable without a
clock; the item arms a `single_shot` timer for the long-press deadline.

| Start zone / condition | Outcome |
|---|---|
| left/right/top screen edge | `accepted = false`: event ignored, lipstick's gesture proceeds |
| bottom edge | toolbar reveal progress signals; nothing to the engine |
| content, single finger, no movement past slop for `longPressDuration` | `longPressed`; engine gets touch cancel; rest of sequence stays with Tuuli |
| content, vertical drag when content is already at that edge | engine gets touch cancel, item releases its grab, the Silica flickable takes over → pulley menu |
| anything else | forwarded verbatim; Servo scrolls, flings, pinches, double-tap zooms |

The item keeps the touch/mouse grab (`setKeepTouchGrab`) for every
engine-owned sequence, which is what stops the enclosing `SilicaFlickable`
from stealing drags.

`InputMethodState` (`ime.rs`) is the state machine behind the hidden QML
`TextInput` Maliit attaches to, published to QML as
`WebView.inputMethod` (`InputMethodProxyObject`; spec 6.3).  The engine's
IME requests set the hints and enter-key type; each committed edit in the
proxy is diffed against the engine's text (`diff_text`) and expressed as
arrow keys, backspaces and a committed composition (`plan_ime_edit`),
because the engine has no "set selection" entry point.  The item adjusts
the engine's viewport rect and scrolls the caret rect into view when the
keyboard shows, without resizing the surface.

## Models and persistence

- `SessionStore` writes atomically (temp file + rename) on a 5 s debounce
  that the Qt layer arms with `single_shot` when the core reports
  `SessionSaveRequested`, on every backgrounding and on `aboutToQuit`,
  with a `clean_exit` flag so a crash is detected on the next start (spec
  8.4).  Private tabs are never written (spec 7.3).
- `TabList` keeps at most `maxLiveWebViews` engine webviews alive,
  evicting least-recently-used non-current tabs; evicted tabs keep their
  state and are re-created on activation.
- History and bookmarks are SQLite via rusqlite (bundled); private tabs
  never write history.
- `PermissionStore` is denied-by-default JSON per origin; private tabs read
  it but never write it.  Request objects handed to QML deny, dismiss or
  reject themselves when dropped unanswered.
- Downloads are performed by the engine; `DownloadManager` picks a unique
  destination and mirrors progress to Nemo Transfer Engine over D-Bus
  (`org.nemo.transferengine`), except for private tabs.

## Paths

Sailjail permits `~/.local/share/<Org>/<App>` and siblings for the
`OrganizationName`/`ApplicationName` in the `.desktop` file.  With
`org.tuuli`/`browser` that is `~/.local/share/org.tuuli/browser/`, which is
what `AppPaths::xdg()` derives and what `QStandardPaths::AppDataLocation`
would return once the application sets those names.  The spec's
`~/.local/share/tuuli/` would not be reachable inside the sandbox, so the
sailjail-derived path is used and the spec text should be read with that
substitution.

## Qt 5.6

qttypes and qmetaobject-rs build against the Qt found through `qmake` (or
`QT_INCLUDE_PATH`/`QT_LIBRARY_PATH` when cross-compiling) and require Qt
≥ 5.6, which is exactly the SDK target's Qt.  Only Qt 5.6 API is used
from the `cpp!` blocks and the QML; the Sailfish CI job builds on the SDK
target to keep that honest.
